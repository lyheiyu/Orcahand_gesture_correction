## What The Code Actually Implements

## 1. Rule-Based Conversion To 17 Actuator Values

The `corrected` representation is generated by:

1. computing geometric hand features from the 21 MediaPipe landmarks;
2. converting those features to normalized flexion/abduction/opening variables;
3. mapping them into the ORCA actuator ranges.

The output dimension is 17 because the right-hand ORCA embodiment exposes 17 actuators in the current `v2` model.

The mapping is implemented in `OrcaFeatureProjector.corrected_vector()`.

Important detail:

- the wrist uses `_set_signed_neutral()` with `-features.wrist`;
- flexion-like terms use `_set_unit()`;
- abduction-like terms use `_set_signed()` or `_set_signed_neutral()`;
- the result is clipped to `env.action_low` and `env.action_high`.

This is a hand-designed embodiment-aware projection, not PCA and not an optimized inverse-kinematics solution.

## 2. MuJoCo Forward Kinematics

The optimizer does not use full dynamics. It uses MuJoCo forward kinematics by:

- resetting MuJoCo data with `mujoco.mj_resetData()`;
- writing actuator values into the corresponding `qpos` entries;
- copying the same values into `data.ctrl`;
- zeroing `qvel`;
- calling `mujoco.mj_forward()`.

This is implemented in:

- `MujocoHandPoseOptimizer._set_pose_from_action()`

The optimized hand points are then read from:

- body positions `data.xpos[...]`
- joint anchor positions `data.xanchor[...]`

So the code is a forward-kinematics-constrained pose fitting procedure, not a dynamics-based physical simulation or inverse dynamics solver.

## 3. Sparse Points Used By The Optimizer

A very important implementation detail is that the optimization does **not** compare all 21 landmarks directly in the landmark loss.

The sparse points used in the objective are only:

- wrist
- thumb tip
- index MCP
- index tip
- middle MCP
- middle tip
- pinky MCP
- pinky tip

This is defined by:

- `MujocoHandPoseOptimizer._POINT_LABELS`
- `MujocoHandPoseOptimizer._target_sparse_points()`
- `MujocoHandPoseOptimizer._forward_sparse_points()`

Therefore:

- `Optimized Action` is fitted against a sparse subset of landmarks;
- `Optimized Full` is a reprojected 21-point hand reconstructed from the optimized actuator state.

This is a paper-to-code discrepancy if the paper text implies direct fitting of all 21 landmarks.

## 4. Actual Objective Function Implemented

Let:

- `a` be the current 17D actuator vector;
- `a_init` be the clipped heuristic initialization from `corrected_vector()` unless an explicit `initial_action` is given;
- `a_prev` be the previous optimized actuator vector;
- `a_prevprev` be the actuator vector two frames back;
- `a_default` be the default actuator pose from MuJoCo `qpos0`, clipped to actuator bounds;
- `s_i(a)` be the predicted sparse point;
- `t_i` be the target sparse point from normalized MediaPipe landmarks;
- `n(a)` be the predicted palm normal;
- `n_t` be the target palm normal;
- `l_i`, `h_i` be actuator lower/upper bounds.

The total objective is:

\[
L(a)
=
\lambda_l L_{\text{landmark}}
+ \lambda_p L_{\text{palm}}
+ \lambda_r L_{\text{prior}}
+ \lambda_t L_{\text{temporal}}
+ \lambda_a L_{\text{acceleration}}
+ \lambda_d L_{\text{default}}
+ \lambda_b L_{\text{boundary}}
\]

with default weights from `OptimizationWeights`:

- landmark: `1.0`
- palm: `0.2`
- prior: `0.3`
- temporal: `0.1`
- acceleration: `0.15`
- default pose: `0.15`
- boundary: `0.05`
- huber delta: `0.08`

## 5. Exact Loss Formulas In Code

### 5.1 Landmark / Huber loss

Implemented in `MujocoHandPoseOptimizer._landmark_loss()`.

For each sparse point label and each coordinate component:

\[
r = s_i(a) - t_i
\]

If `huber_delta <= 0`, the code uses pure squared error:

\[
L_{\text{landmark}} = \sum_i \|r_i\|_2^2
\]

Otherwise, the code applies elementwise Huber:

\[
\rho_\delta(r)
=
\begin{cases}
\frac{1}{2}r^2, & |r| \le \delta \\
\delta (|r| - \frac{1}{2}\delta), & |r| > \delta
\end{cases}
\]

and sums across all sparse-point coordinates.

### 5.2 Palm-normal loss

Implemented inside `loss_terms()`:

\[
L_{\text{palm}} = \|n(a) - n_t\|_2^2
\]

### 5.3 Prior loss

Implemented inside `loss_terms()`:

\[
L_{\text{prior}} = \|a - a_{\text{init}}\|_2^2
\]

### 5.4 Temporal loss

If `prev_action` is available:

\[
L_{\text{temporal}} = \|a - a_{\text{prev}}\|_2^2
\]

Otherwise it is exactly zero.

### 5.5 Acceleration loss

If both `prev_action` and `prev_prev_action` are available:

\[
L_{\text{acceleration}}
=
\|a - 2a_{\text{prev}} + a_{\text{prevprev}}\|_2^2
\]

Otherwise it is exactly zero.

### 5.6 Default-pose loss

This term is fully defined in code, although it was under-specified in the paper:

\[
L_{\text{default}} = \|a - a_{\text{default}}\|_2^2
\]

where:

\[
a_{\text{default},i}
=
\text{clip}(qpos0_i, l_i, h_i)
\]

and `qpos0_i` is the MuJoCo default joint position associated with actuator `i`.

### 5.7 Boundary loss

This term is also fully defined in code.

First the code normalizes each actuator into `[0, 1]`:

\[
u_i = \frac{a_i - l_i}{h_i - l_i}
\]

Then it penalizes values inside the outer 10 percent of the range:

\[
L_{\text{boundary}}
=
\sum_i
\left[
\max(0, 0.1 - u_i)^2
+
\max(0, u_i - 0.9)^2
\right]
\]

So:

- no penalty when `u_i` is between `0.1` and `0.9`;
- quadratic penalty near the lower or upper actuator boundary.

## Alignment Between MediaPipe Landmarks And MuJoCo Points

## 1. Origin

Both target MediaPipe landmarks and MuJoCo-reconstructed landmarks are translated so that:

- the wrist is at the origin.

MediaPipe side:

- `gesture_features.normalize_landmarks()`

MuJoCo side:

- `MujocoHandPoseOptimizer._normalize_world_points()`
- `MujocoHandPoseOptimizer._forward_sparse_points()`

## 2. Scale

Both sides use the same normalization idea:

- compute palm width from index MCP to pinky MCP;
- compute palm length from wrist to middle MCP;
- use `max(palm_width, palm_length, 1e-6)` as scale.

So the comparison is translation-normalized and scale-normalized.

## 3. Coordinate-axis directions

There is **no explicit rigid rotation alignment** or coordinate-frame calibration between MediaPipe and MuJoCo inside the optimizer.

The optimizer assumes that once the landmarks are translated and scaled, the axes are already comparable.

This means:

- origin and scale are aligned;
- axis directions are **not** explicitly reoriented inside the optimizer;
- there is no Procrustes alignment, no estimated rotation matrix, and no camera-frame-to-hand-frame solve.

## 4. Left/right hand handling

The optimizer itself is hard-coded to:

- `OrcaHandRight`

and the actuator names are all right-hand actuator names.

Therefore the current optimization implementation is effectively:

- right-hand only.

Any left/right normalization or camera-side reinterpretation happens outside the optimizer, for example in teleoperation code.

## 5. Landmark-to-MuJoCo correspondence

### Sparse correspondence used by the loss

Only eight points are used:

- wrist
- thumb tip
- index MCP
- index tip
- middle MCP
- middle tip
- pinky MCP
- pinky tip

### Full 21-point reconstruction

`Optimized Full` is assembled from:

- body positions for tips and wrist;
- joint anchors for intermediate joints.

This gives a 21-point hand in MediaPipe-like indexing order, but those full 21 points are **not** all directly supervised by the optimization objective.

- the code correctly resets previous-frame state at new-sequence boundaries;
- this reset matters and is not a trivial detail.

## 5. Delay or excessive smoothing

There is no non-causal lookahead in the optimizer.

The optimization only uses:

- the current observation;
- the previous optimized action;
- the action two frames back.

Therefore it is a causal frame-wise optimizer, not a future-looking smoother.

A simple lag check across the three tested sequences found:

- best correlation lag was usually `0` frames for almost all actuators;
- one outlier actuator occasionally showed a best lag of `-3`, but the dominant pattern was lag `0`.

Mean best lag:

- `01fd6a3af833`: `-0.1875` frames
- `04e16016884a`: `-0.1875` frames
- `065ced8f3f3c`: `0.0` frames

At the same time, motion amplitude is clearly attenuated:

- optimized mean actuator velocity is about `0.49` to `0.53` of the heuristic corrected velocity on the three tested sequences.

So the code does not show evidence of explicit multi-frame delay, but it does apply strong smoothing/inertia in actuator space.

## Classification Pipeline Leakage Check

## 1. Train/test splitting by sequence rather than frame

In sequence mode, `train_svm.py`:

- groups frames by `sequence_id`;
- creates one aggregated sample per sequence;
- splits on sequence indices, not frame rows.

This is correct with respect to frame leakage.

## 2. StandardScaler fitting

### Without PCA

The classifier pipeline is:

- `Pipeline([('scaler', StandardScaler()), ('model', estimator)])`

Since the pipeline is fit on `x_train`, the scaler is fit on training data only.

### With PCA in frame mode

The code explicitly does:

- `scaler.fit_transform(x_train)`
- `scaler.transform(x_test)`
- `pca.fit_transform(x_train_scaled)`
- `pca.transform(x_test_scaled)`

So both scaler and PCA are fit on training data only.

### With PCA in sequence mode

The code concatenates only training-sequence frames, then fits:

- `StandardScaler()` on training frames only;
- `PCA()` on training frames only;
- applies that fitted transform to test-sequence frames.

This is also correct.

## 3. Identical splits across representations

For the same dataset, same random seed, and same sequence labels/order:

- raw and corrected produced identical sequence ordering;
- the resulting train/test sequence indices were identical.

Diagnostic result:

- identical sequence order raw vs corrected: yes
- identical train indices for same seed: yes
- identical test indices for same seed: yes

Therefore there is no obvious representation-dependent split mismatch in the current sequence-mode classification pipeline.

## Confirmed Paper-To-Code Inconsistencies

## 1. The landmark loss is not a full 21-landmark loss

The code optimizes only a sparse 8-point subset, not all 21 landmarks directly.

Impact:

- any paper statement implying direct full-landmark fitting is inaccurate;
- `Optimized Full` is a reconstruction from the latent actuator state, not a directly supervised 21-point fit.

## 2. The optimizer is right-hand-only

The current optimizer uses `OrcaHandRight` and right-hand actuator names only.

Impact:

- any paper wording suggesting symmetric left/right support would be overstated.

## 3. Alignment is translation-and-scale only

The code aligns origin and scale, but it does not estimate an extra rotation or camera-to-hand transform inside the optimizer.

Impact:

- if the paper suggests stronger coordinate-frame alignment, that should be weakened.

## Confirmed Bugs

## 1. Palm-normal sign inconsistency

This is the most important confirmed issue.

The target palm normal is computed in `gesture_features.palm_normal_vector()` as:

\[
n_t \propto \text{cross}(\text{palm\_forward}, \text{palm\_across})
\]

But the predicted palm normal in `MujocoHandPoseOptimizer._forward_sparse_points()` is computed as:

\[
n(a) \propto \text{cross}(\text{palm\_across}, \text{palm\_forward})
\]

These are negatives of each other.

Synthetic consistency check from a valid MuJoCo-generated hand:

- target normal dot current normal: `-0.9986`
- perfect palm loss: `3.9972`

This means:

- even if the hand pose is already correct, the palm-normal term cannot go near zero;
- the optimizer is penalized for matching the true palm orientation under its own current convention.

Impact:

- the palm loss is systematically inconsistent with the target normal definition;
- this can bias the optimizer away from otherwise correct solutions;
- it helps explain the poor synthetic recovery result.

This should be treated as a real implementation bug, not just a wording issue.

## Overall Assessment

The current code does match the broad paper story in several important ways:

- there is a heuristic `corrected` actuator projection;
- optimization is done in ORCA actuator space;
- MuJoCo forward kinematics is used to evaluate candidate poses;
- temporal and acceleration regularization are present;
- `Optimized Action` and `Optimized Full` are exported exactly as described at a high level.

However, there are also significant code-level realities that the paper must reflect more precisely:

- the fitting is sparse, not full 21-landmark fitting;
- alignment is only translation plus scale normalization;
- the implementation is right-hand-only;
- the palm-normal loss currently contains a confirmed sign bug.

So the project logic is not fundamentally wrong, but the current implementation and current paper wording are not yet fully aligned, and the palm-normal term should be corrected before relying on it as evidence of a well-posed objective.
